# Техническое задание на доработку проекта "Космическая Станция Максима"

Дата проверки: 2026-05-18

## 1. Цель документа

Документ фиксирует найденные ошибки, расхождения с `README.md` и план доработки. Код проекта в рамках проверки не исправлялся.

## 2. Краткий итог проверки

Текущее состояние нельзя считать готовым к стабильному использованию:

- фронтенд не проходит production-сборку `npm run build`;
- сервер собирается, но тестовый запуск `npm test -- --run` падает из-за запуска тестов из `dist`;
- бизнес-логика энергии и затухания не совпадает с описанием в `README.md`;
- часть пользовательских сценариев визуально есть, но не работает полностью: смена PIN, переход к барабану последствий, корректная синхронизация сундуков после CRUD;
- есть риск некорректного учета streak/сундуков, ночного decay и SSE-обновлений.

## 3. Проверенные команды

- `npm run build` в корне: ошибка TypeScript, фронтенд не собирается.
- `npm run build` в `server`: успешно.
- `npm test -- --run` в `server`: 6 тестов проходят, но общий запуск падает на `dist/src/services/energy.test.js`.

## 4. Критические доработки

### 4.1. Починить сборку фронтенда

Проблема: `npm run build` падает на TypeScript-ошибках.

Найдено:

- `src/screens/MissionLogScreen.tsx` использует `deleteEvent`, но в интерфейсе `AppState` его нет: `src/store.tsx:5-22`, `src/store.tsx:193-205`.
- `chestStatus` в типе стора не содержит статус `completed`, но UI его проверяет: `src/store.tsx:14-17`, `src/screens/ChildMainScreen.tsx:178`, `src/screens/ChildMainScreen.tsx:208`.
- `setChests(mappedChests)` получает элементы со статусом типа `string`, а не union-типом `locked | active | cooldown`: `src/store.tsx:103-111`.
- Есть неиспользуемые импорты/переменные при `noUnusedLocals`: `AdminChestsScreen`, `ChildMainWarningScreen`, `ChildMainDangerScreen`, `ChildMainCriticalScreen`.

Требование:

- Привести `AppState` к реальному публичному API стора.
- Добавить `completed` в типы статусов сундуков.
- Типизировать маппинг сундуков без `as any`.
- Убрать неиспользуемые переменные или использовать их в UI.
- Критерий готовности: `npm run build` в корне завершается успешно.

### 4.2. Исправить маршрут барабана последствий

Проблема: кнопка последствий ведет на `/drum-danger`, но в роутере зарегистрирован `/drum2`.

Найдено:

- Переход: `src/screens/ChildMainScreen.tsx:196`.
- Роут: `src/App.tsx:38`.

Требование:

- Выбрать один канонический путь и синхронизировать роутер, кнопки и документацию.
- Критерий готовности: доступный сундук последствий открывает экран `DrumDangerScreen`.

### 4.3. Синхронизировать модель энергии с README

Проблема: `README.md` описывает формулу `E = 100 * (1 - e^(-k * S))` и временное decay-взвешивание, но код использует логистическую формулу и простую сумму событий за последние 7 дней.

Найдено:

- Описание README: `README.md:12-15`.
- Реальная формула: `server/src/services/energy.ts:1-4`.
- Реальная агрегация: `server/src/services/energy.ts:14-23`.
- Использование в состоянии станции: `server/src/services/station.ts:23-31`.

Требование:

- Принять продуктово один вариант: либо обновить README под текущую логистическую модель, либо реализовать описанную экспоненциальную модель.
- Уточнить смысл `curveK`: сейчас это делитель в логистической формуле, а не множитель `k`.
- Покрыть расчет энергии и сфер тестами на реальные ожидаемые значения.

### 4.4. Исправить логику decay

Проблема: в настройках есть `decayCoeff`, UI объясняет ночное затухание, но текущая система одновременно использует 7-дневное окно и отдельное системное событие decay. Это может искажать расчет и создает конфликт с описанием "старые события постепенно забываются".

Найдено:

- `decayCoeff` в настройках: `server/prisma/schema.prisma`, `server/src/routes/settings.ts:14-24`.
- Ночной job добавляет событие `type: decay`: `server/src/jobs/decay.ts:12-24`.
- `calcCurrentS(k)` игнорирует параметр `k`: `server/src/services/station.ts:77-80`.
- Системный пользователь `authorId: 0` зависит от seed: `server/src/jobs/decay.ts:21`.

Требование:

- Определить единую механику decay: математическое затухание при расчете или отдельные системные события, но не смешивать без четкой модели.
- Если остаются системные события, гарантировать наличие system user при старте и исключить сферу `system` из пользовательских сценариев.
- После decay отправлять SSE-обновление, иначе экран ребенка ночью не обновится.

### 4.5. Исправить расчет streak и уровней сундуков

Проблема: `calcStreakInfo` считает каждый день по скользящему 7-дневному окну, а не по фактическому состоянию энергии на конец каждого дня с учетом выбранной decay-модели. Это может давать неверные streak-дни.

Найдено:

- Скользящее окно внутри streak: `server/src/services/streak.ts:21-35`.
- Подсчет уже открытых сундуков с даты начала streak: `server/src/services/station.ts:43-60`.

Требование:

- Формально описать правило streak: день считается, если энергия на конец дня была выше/ниже порога.
- Рассчитывать streak через единую функцию исторического состояния энергии.
- Покрыть тестами сценарии: порог достигнут сегодня, удержан 1/7/14/30 дней, streak сброшен, spin внутри streak, spin до streak не учитывается.

## 5. Важные доработки

### 5.1. Привести SSE к одному контракту

Проблема: README говорит, что клиент слушает `/api/station/stream` и получает событие `state_update`, а код использует `/api/sse/station` и обычный `onmessage`.

Найдено:

- README: `README.md:36`, `README.md:89-90`.
- Клиент: `src/store.tsx:143-152`.
- Сервер: `server/src/routes/sse.ts`.
- `/api/events` отправляет просто state, а `/api/spin` отправляет `{ type, data }`: `server/src/routes/events.ts`, `server/src/routes/spin.ts:48-50`.

Требование:

- Выбрать единый формат SSE-сообщения.
- Если используется `{ type: 'state_update', data }`, клиент должен применять `data`, а не весь объект.
- Все мутации состояния должны отправлять одинаковый формат.

### 5.2. Синхронизировать сундуки после добавления и удаления

Проблема: CRUD сундуков меняет БД, но не обновляет общий store и не рассылает SSE. Барабан может оставаться со старым списком до перезагрузки приложения.

Найдено:

- API CRUD сундуков: `server/src/routes/chests.ts:12-35`.
- Store загружает сундуки только при первичном fetch: `src/store.tsx:86-111`.

Требование:

- После POST/DELETE сундука обновлять список в store.
- Рассмотреть SSE-событие или повторный fetch на экранах барабана.
- Обработать удаление сундука, который уже связан со `SpinResult`.

### 5.3. Реализовать смену PIN или убрать UI

Проблема: UI смены/сброса PIN есть, но кнопка только очищает форму. Серверных эндпоинтов для смены PIN нет.

Найдено:

- Settings API не принимает PIN: `server/src/routes/settings.ts:14-24`.
- Auth API содержит только login: `server/src/routes/auth.ts:7-34`.

Требование:

- Добавить защищенный endpoint смены PIN.
- Для `papa`: проверять старый PIN.
- Для сброса `mama`/`babushka`: разрешать только роли `papa`.
- Убрать debug fallback `papa/1111` из production-режима или явно ограничить dev-режимом.

### 5.4. Валидация входных данных на сервере

Проблема: сервер почти не валидирует бизнес-поля.

Найдено:

- `POST /events` проверяет только наличие полей: `server/src/routes/events.ts`.

Требование:

- Валидировать `sphere`, `type`, `weight`, `chestType`, `level`, строки настроек и диапазоны порогов.
- Проверять, что выбранный вес входит в соответствующий список настроек.
- Возвращать понятные ошибки для UI.

### 5.5. Устранить локальный fallback, который скрывает ошибки

Проблема: при ошибке API добавление события продолжает локально менять интерфейс, хотя запись в БД не создана.

- HTTP-проверка через `curl` из текущей sandbox-среды не смогла подключиться к `localhost:80` и `localhost:3001`, хотя браузер Codex страницу открыл.

- Это означает, что проект на машине пользователя запущен, но терминальная sandbox-среда не имеет полного доступа к Docker/локальной сети.

### 9.3. Нужно ли сейчас что-то перезапускать

Если `http://localhost/` у пользователя открывается, срочный перезапуск не нужен.

Перезапуск имеет смысл делать перед началом исправлений или если интерфейс зависнет/перестанет видеть API.

Рекомендуемые команды для пользователя в терминале проекта:

```bash
docker compose ps
docker compose logs -f server frontend postgres
docker compose restart
```

Если нужно пересобрать все контейнеры:

```bash
docker compose up --build -d
```

Если Docker не используется и запуск идет вручную, удобнее запускать так:

```bash
cd server
npm install
npm run dev
```

В отдельном терминале:

```bash
npm install
npm run dev -- --host 0.0.0.0 --port 5173
```

Тогда фронтенд будет на `http://localhost:5173`, а backend на `http://localhost:3001`.

### 2026-05-19: Этап 2-3, единая модель энергии, decay и streak

Статус: выполнено на уровне backend-логики и тестов.

Принятое решение:

- Оставлена текущая bounded-логистическая формула энергии `E = 200 / (1 + exp(-S / k)) - 100`, потому что она симметрично ограничивает энергию диапазоном от `-100` до `+100`.
- Формула из старого README в виде `100 * (1 - e^(-k * S))` не взята как рабочая, потому что без дополнительной нормализации она плохо подходит для отрицательных значений.
- Decay теперь считается на лету по возрасту каждого события: `weight * decayCoeff ^ ageDays`.
- Резкого обнуления через 7 дней больше нет.
- Ночные системные события `type: decay` больше не создаются, чтобы не было двойного учета decay.

Сделано:

- Добавлена функция `calcDecayedSum` в `server/src/services/energy.ts`.
- `getStationState` теперь считает общую энергию и сферы через `calcDecayedSum`.
- `calcStreakInfo` теперь считает streak по исторической энергии на конец каждого дня, а не по скользящему 7-дневному окну.
- Ночной cron больше не пишет искусственное событие в БД, а только рассылает актуальное состояние открытым клиентам.
- `POST /api/spin` теперь отправляет в SSE такой же plain-state формат, как `/api/events`, без `{ type, data }`, чтобы клиент не ломался на разных форматах.

### 2026-05-19: Исправление повторного достижения зоны и сундуков на 0 дней

Статус: выполнено.

Контекст бага:

- При `rewardDays = 0,...` сундук должен становиться доступным сразу, как только энергия вошла в нужную зону.
- Если ребенок уже входил в зону, потом откатился и снова вернулся, уровни сундуков должны начинаться заново с первого уровня.
- Раньше backend привязывал старт streak к началу календарного дня, поэтому старые spin-записи того же дня могли ошибочно считаться частью нового достижения.

Сделано:

- `calcStreakInfo` теперь определяет начало текущей zone-session по событию, которое вернуло энергию в нужную зону, а не по `00:00` текущего дня.
- Если энергия сейчас вне зоны, streak возвращает `startDate: null`.
- `calcChestStatus` теперь принимает явный флаг `isInZone`, чтобы корректно различать:
  - `0 дней и вне зоны` -> `locked`;
  - `0 дней и в зоне` -> `available`.
- `getStationState` передает в `calcChestStatus` факт нахождения в зоне через наличие `startDate`.
- Счетчик уже открытых сундуков теперь считается от точного момента нового входа в зону, поэтому повторное достижение после отката стартует заново.

Добавлены тесты:

- `0` дней в зоне сразу делает сундук `available`.
- `0` дней вне зоны остается `locked`.
- Повторный вход в зону после отката в тот же день стартует новую session от нового события.
