# Космическая Станция Максима

Геймифицированная система привычек для ребенка. Родители фиксируют события, приложение пересчитывает энергию космической станции, сферы развития, streak-дни и доступность сундуков наград или последствий.

## Текущее состояние

Проект работает через Docker Compose:

- frontend: React/Vite на `http://localhost`;
- backend API: Fastify на `http://localhost:3001/api`;
- database: PostgreSQL на `localhost:5432`.

Код уже приведен к рабочему базовому состоянию: frontend собирается, backend собирается, серверные тесты проходят. Подробный журнал работ и оставшиеся пункты лежат в [TECHNICAL_REVIEW_PLAN.md](./TECHNICAL_REVIEW_PLAN.md).

## Быстрый запуск

1. Создать `.env` в корне проекта по примеру `.env.example`.
2. Запустить контейнеры:

```bash
docker compose up --build -d
```

3. Открыть приложение:

```text
http://localhost
```

При старте server-контейнер выполняет:

```bash
npx prisma db push
npx prisma db seed
npm run dev
```

Seed создает системного пользователя, родительские роли, настройки и стартовый набор предметов сундуков для всех уровней. Существующие события, spin-история и уже добавленные сундуки seed не очищает.

Если менялся backend-код или seed:

```bash
docker compose up --build -d
```

Если менялся только frontend-код, текущий Docker-режим с volume обычно подхватывает изменения через Vite, но перед финальной проверкой все равно лучше пересобрать compose.

## Production deploy

Production-адрес приложения:

```text
https://max.kozyura.space
```

Production API работает через тот же домен:

```text
https://max.kozyura.space/api
```

Для production frontend должен обращаться к API по относительному адресу:

```text
VITE_API_URL=/api
```

DNS для поддомена:

```text
A  max  <IP production-сервера>
```

Для текущего сервера:

```text
A  max  5.129.218.37
```

HTTPS лучше держать на reverse proxy, например Caddy. Снаружи должны быть открыты только `80` и `443`; backend-порт `3001` не должен быть публичным.

Пример Caddy-конфига:

```caddyfile
max.kozyura.space {
  reverse_proxy /api/* server:3001
  reverse_proxy frontend:80
}
```

Порядок обновления production:

1. Залить изменения в GitHub и смерджить нужную ветку.
2. На сервере обновить код:

```bash
cd /opt/station-maksim
git fetch origin
git checkout main
git pull origin main
docker compose up --build -d
```

Если деплой идет не из `main`, а из отдельной ветки, заменить `main` на нужное имя ветки, например:

```bash
git checkout codex/final-station-release
git pull origin codex/final-station-release
```

Быстрая проверка после деплоя:

```bash
docker compose ps
curl -I https://max.kozyura.space
curl https://max.kozyura.space/api/station
```

## Роли и PIN

Стандартные роли после seed:

- `papa` / `1111`
- `mama` / `2222`
- `babushka` / `3333`

Вход находится на `/admin`. Смена PIN доступна в `/admin/settings`:

- папа может сменить свой PIN только со старым PIN;
- папа может сбросить PIN мамы и бабушки;
- мама и бабушка не имеют доступа к системным настройкам.

Debug fallback `papa/1111` работает только при:

```text
ALLOW_DEBUG_PIN=true
```

В обычном режиме вход идет только по PIN из базы.

## Основная логика

Родители добавляют события по сферам:

- `study` — учеба;
- `respect` — уважение;
- `focus` — фокус;
- `home` — семья.

Событие имеет тип и вес:

- `good` — положительное;
- `neutral` — нейтральное;
- `bad` — отрицательное.

Сумма событий считается с временным затуханием:

```text
S = sum(weight * decayCoeff ^ ageDays)
```

Энергия считается bounded-логистической формулой:

```text
E = 200 / (1 + exp(-S / curveK)) - 100
```

Итог округляется до 0.1 и остается в диапазоне `-100..100`.

Сферы считаются той же моделью, но только по событиям своей сферы, и отображаются как `0..100%`.

Ночной cron больше не создает искусственные `decay`-события. Он только рассылает актуальное состояние через SSE, чтобы клиенты видели эффект временного затухания.

## Сундуки и streak

Есть два типа сундуков:

- `reward` — награды при положительной энергии;
- `consequence` — последствия при отрицательной энергии.

Состояния станции переключаются по фиксированным зонам энергии и не настраиваются в админке:

- `-100..-50` — критическое состояние;
- `-50..0` — опасное состояние;
- `0..50` — предупреждение;
- `50..100` — хорошее состояние.

Пороги сундуков настраиваются отдельно по уровням:

- `rewardEnergyThresholds` и `rewardDays` задают энергию и дни удержания для каждого уровня наград;
- `consequenceEnergyThresholds` и `consequenceDays` задают энергию и дни удержания для каждого уровня последствий.

Каждый следующий уровень сундука проверяется отдельно. Например, если для награды уровня 2 задано `E >= 70` и `7` дней, отсчет идет только пока энергия держится на `70` или выше. Для последствий логика зеркальная: если для уровня задано `E <= -60`, отсчет идет только пока энергия держится на `-60` или ниже.

Streak считается по исторической энергии и по текущей zone-session соответствующего уровня. Если ребенок вышел из нужной энергетической зоны и потом вернулся, новая session начинается заново. Для `0` дней сундук становится доступным сразу при входе в нужную зону.

Статусы сундуков:

- `locked` — нужный энергетический порог уровня еще не достигнут;
- `countdown` — порог удерживается, но дней еще не хватает;
- `available` — сундук можно открыть;
- `completed` — все уровни текущего streak уже получены.

На главной под сундуками отображается следующий уровень: если энергии не хватает, показывается требуемый уровень `E`; если энергия уже в нужной зоне, показываются оставшиеся дни и прогресс-бар удержания.

Формат countdown в UI:

```text
ДО УР.{N} ОСТАЛОСЬ {X} ДНЕЙ
```

## Барабаны

Маршруты:

- `/drum` — барабан наград;
- `/drum-danger` — барабан последствий;
- `/drum2` — legacy alias для `/drum-danger`.

Защита работает в двух местах:

- frontend не пускает прямым URL на недоступный барабан и возвращает на `/`;
- backend в `POST /api/spin` еще раз проверяет актуальную доступность сундука.

После успешного spin backend сохраняет `SpinResult` и рассылает новый state. Frontend фиксирует начатую прокрутку и список предметов на момент свайпа, поэтому обновление `chestStatus` не прерывает анимацию. Пользователь видит выпавшую награду или последствие и возвращается на главную только после кнопки `ЗАБРАТЬ!` или `ПРИНЯТЬ!`.

## Frontend-маршруты

Child:

- `/` — автоматический выбор состояния станции;
- `/warning`;
- `/danger`;
- `/critical`;
- `/drum`;
- `/drum-danger`;
- `/drum2`;
- `/log`.

Admin:

- `/admin` — вход по роли и PIN;
- `/admin/event` — добавление события;
- `/admin/chests` — управление предметами сундуков;
- `/admin/settings` — настройки системы и PIN.

Все child-экраны используют общий компонент отображения сундуков, чтобы статусы не расходились между состояниями станции.

## API

Public:

- `GET /api/station`
- `GET /api/chests`
- `GET /api/events`
- `GET /api/events?type=spins`
- `POST /api/auth/login`
- `GET /api/sse/station`
- `POST /api/spin`

Protected:

- `POST /api/events`
- `DELETE /api/events/:id`
- `POST /api/chests`
- `DELETE /api/chests/:id`
- `GET /api/settings` — только `papa`
- `PUT /api/settings` — только `papa`
- `PUT /api/auth/pin` — только `papa`

`POST /api/spin` сейчас публичный, но не позволяет открыть недоступный сундук: сервер проверяет `chestStatus` перед созданием `SpinResult`.

## Realtime

Клиент подключается к:

```text
GET /api/sse/station
```

Основной формат SSE — plain JSON state. Клиент также поддерживает старый формат:

```json
{ "type": "state_update", "data": {} }
```

SSE-обновления отправляются после:

- добавления или удаления события;
- spin сундука;
- добавления или удаления предмета сундука;
- изменения настроек;
- ночного cron tick.

## Данные

Основные таблицы:

- `User`
- `Event`
- `ChestItem`
- `SpinResult`
- `Settings`

`SpinResult` хранит историю открытий сундуков. Если предмет сундука уже есть в истории spin, `DELETE /api/chests/:id` вернет `409`, чтобы не ломать журнал.

## Подготовка к реальному использованию

Перед семейным использованием стоит:

- удалить тестовые события и тестовые spin-записи из живой базы;
- проверить, что в `/admin/chests` есть реальные награды и последствия для всех уровней;
- заменить стартовые PIN;
- проверить оба барабана после `docker compose up --build -d`;
- проверить realtime-синхронизацию в двух вкладках.

Для полного сброса локальной Docker-базы можно удалить volume PostgreSQL и поднять compose заново. Это уничтожит все события, PIN, сундуки и историю:

```bash
docker compose down -v
docker compose up --build -d
```

Используйте этот сброс только для разработки или перед чистой первичной настройкой.

## Известные ограничения

- Frontend unit-тесты пока не настроены; frontend проверяется через TypeScript/build и ручной QA.
- `/api/spin` остается публичным endpoint, хотя серверная проверка доступности сундука уже защищает бизнес-правило.
- Админские формы еще можно улучшить по отображению API-ошибок, например при попытке удалить предмет, уже использованный в spin-истории.
